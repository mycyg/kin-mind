# Local speech replies

A public reply can carry `presentation: {mode: "text" | "voice" | "both", style: ""}` alongside its existing `private_note`, `action`, and `bubbles`. Omitting it keeps text behavior. Kin chooses text or voice in the same response, without automatically repeating the same content in both forms. Both is reserved for an explicit request for a transcript or both forms; the current owner's explicit choice takes precedence over older preferences. Everyday chat favors short, natural exchanges; work and requested detail remain complete. No fixed character or bubble count is imposed. The instructions and examples select presentation before writing public wording in the same response. Voice and both are composed as speakable conversation, with context-appropriate interjections, phrasing and pauses, without emoji, kaomoji or parenthetical acting directions. Text keeps its normal chat style. There is no separate planning request, symbol-stripping pass, or new output validation layer.

Private notes are saved and removed at the existing boundary. Only public bubble text and the separate short style instruction reach the local synthesizer. The same presentation field is carried by proactive drafts. A bubble object may supply its own `presentation` alongside `text` and `references`; omitted or null inherits the envelope form. This allows different content to use different forms without content hashing or duplicate filtering.

The host's private `mind-config.json` configures `tts.python`, `tts.model`, `tts.ffmpeg`, and either `tts.voice` for CustomVoice or `tts.referenceAudio` plus `tts.referenceText` for Base reference generation. The current installation uses an existing local Base model and the exact synthetic audio selected by the owner. The recording is kept outside the public repository. No credentials or model downloads are required. A lazy child worker loads once, processes requests sequentially, and exits when its host closes stdin. Completed Opus files use existing transport IDs for resume.

Base reference generation uses a fixed audio/transcript context with temperature 0.3 and top_p 0.9; it does not use CustomVoice `instruct` or an unsupported numeric speed factor. Expression follows public wording and punctuation. The `style` field remains for compatibility but is not applied in reference mode. A fixed reference improves identity conditioning, but acoustic similarity and naturalness still need listening evaluation; a seed is not a guarantee. Existing CustomVoice configurations retain their previous behavior.

Each ordinary reply remains one logical bubble. Voice adds one speech fragment; both retains text fragments followed by speech. Existing receipts decide delivery. A synthesis failure is `tts-failed`, with accepted text retained as partial delivery; it becomes an existing reply outcome/tail fact rather than a successful reply. Proactive contacts retain accepted items and expose the failure on their settlement. No automatic text replacement or new retry loop is added.

Feishu uploads with `file_type=opus` and sends `msg_type=audio`. WeChat ordinary reply media uses its existing file uploader and `FILE` message, never a claimed native voice bar. The current deployment routes replies and proactive contacts to Feishu; its receive-only WeChat policy and retired proactive WeChat entry remain in force. Explicit WeChat artifact requests retain their existing path.

Tests use synthetic text, a local worker or channel doubles. Live phone messages require an explicit recipient/content test scope. Local performance samples prove synthesis only, not channel acceptance or perceived voice quality.

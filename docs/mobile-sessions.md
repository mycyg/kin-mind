# Compression-first mobile sessions

For private companion instructions and pinned runtime upgrades, see
[mobile runtime](mobile-runtime.md) ([中文](mobile-runtime.zh.md), [日本語](mobile-runtime.ja.md)).

The host keeps a long-lived logical conversation across its channels. Each native thread is a numbered segment of that conversation. Shared memory, tasks, input IDs and delivery receipts remain in their existing stores.

## Decision order

A session review proposes `keep`, `recall`, `compact`, `defer`, `prepare` or `rotate`. Missing evidence calls for recall. Context pressure calls for compression of the current native thread. A new segment requires a completed compaction in the current generation and specific, still-valid degradation evidence observed afterwards.

The host estimates pressure from the verified effective window, current input usage and reserved output/tool space. Defaults request review at 65%, with 85% classified as critical. Cumulative billing, rollout size, elapsed time, generic warnings and compaction counts do not authorize rotation. A successful compaction preserves the current thread and task IDs. Compaction comes first: after one completes, the next may run once the 30-minute cooldown has passed, and the cooldown only sets that time; it is not a judgment that none is needed.

A local minute tick reads native history incrementally (compaction events and token usage), the router's inputs and tasks and the mind's session snapshot; it calls no model. Each observation has a cause: the binding, the configuration and policy, the serving profile, the window's pressure level, open tasks, pending owner requests, sourced degradation and corrected sources. Dialogue that only grows, a finished compaction and memory entries an appraisal revised are recorded in the observation but do not by themselves ask for a review. A review is asked once per cause, and only when the window is elevated or critical, sourced degradation exists or an owner request is pending. The same cause again is either already answered or asked again after a wait that starts at the compaction cooldown and doubles up to eight hours; a review unanswered for two hours waits the same way, and a request the host could not queue is retried after a wait that grows to an hour. A new cause supersedes the open questions of older ones.

The host writes the observation only when it changes and asks through the `session-review` host action, which queues one maintenance appraisal per observation. That job sees a small operational view and can write only the session judgment; it cannot change affect, wishes, contact preferences or user activity. Normal appraisals may include the same observation. The judgment is validated first (cited observations must exist, findings must quote an owner source exactly, `prepare` and `rotate` must cite the last completed compaction and evidence after it), with one bounded repair, and handed over through `session_advice.submit` in the same transaction: one row per scope in `mind_session_advice`, replaced by the next. The session snapshot the minute tick reads carries it to the registry, which keeps it as `sessionAdvice`. A judgment from a main-session assessment is accepted only when its native receipt matches the current binding and serving profile and a completed assessment turn the host recorded; any other judgment needs a DeepSeek Flash / high receipt. Advice is bound to its observation: a changed cause, such as a task revision, makes it stale before action, while a late answer still settles the question it was asked about.

With dependency-aware semantic commits enabled, one operational session judgment may run while one memory batch is being prepared. The optional `operational_lanes` recovery feature also gives current action judgments a separate worker and lease from enrichment. Commits remain transactional and serialized. A long evidence-compression job therefore cannot block a native-window check or current action assessment. See [mobile recovery](mobile-recovery.md) for migration and progress receipts.

## Checkpoints and budgets

`SessionCheckpoint` joins durable public runtime events with the pending journal. It retains the preceding question, short user answers and associated reply bubbles. Runtime warnings and uncertain sends cannot become successful public dialogue. Repeated user words remain separate events; matching model-output/delivery records can share one displayed utterance.

Full source dependencies, hashes and revisions remain in the private registry. The injected payload contains public dialogue, task identity, recent input dispositions and shared-store reading links. A checkpoint is read by the window that follows a compaction or handover, so the room left in the current window is no measure of it: it starts from the restore budget (2,000 tokens, or 4,000 while tasks are open) and grows to what the recent dialogue and the linked memory it leans on need, never past a fixed ceiling of 8,000 tokens. What fits stays verbatim; otherwise the latest four complete exchanges keep their words as far as the ceiling allows and earlier ones take the sourced DeepSeek summary. A source that neither fits nor is covered by the summary leaves the checkpoint incomplete, which blocks compaction and promotion. The allowance is bookkeeping, part of neither the checkpoint's identity nor its payload. The session manager builds a checkpoint once per cursor state and retries an incomplete one after a wait that starts at five minutes and doubles up to an hour. Original evidence is never replaced or character-truncated.

Automatically injected background has the same fixed ceiling per injection. Without native-window accounting (`native_window_context` off), one native window also takes at most 12,000 tokens of automatic additions. That ledger is separate from native context pressure, and only a native compaction completion resets it. Durable epoch receipts make delayed duplicates harmless, including duplicates from an earlier window. A restored checkpoint is reconciled by its persisted native marker and accounted once. Source corrections invalidate the checkpoint and its dependent summaries.

See [continuity manifests and verified delivery](continuity-manifests.md) for the shared linked working set, pending operation facts, exact native injection receipts, source-dependent caches and independent rollout switches.

## Execution and recovery

| Boundary | Host behavior |
| --- | --- |
| Active native turn, background tool, queued input or pending delivery | Ordinary automatic changes wait and preserve the current profile and work lock. An explicit owner model/mode control may use the confirmed force boundary below |
| Idle work with a complete checkpoint | Compact in the same thread; retain task and input versions |
| Uncertain compaction receipt | Reconcile the native event; do not repeat the operation |
| Candidate creation response is uncertain | Retain the original attempt; do not create another candidate |
| Candidate injection response is uncertain | Check the original marker in native history |
| New input or source revision while preparing | Invalidate the prepared checkpoint before commit |
| Crash after binding commit | Roll forward to the committed generation; never replay accepted input |
| Late output from an old native segment | Keep operation evidence; reject its authority to send |

The session manager shares the model router's dispatch mutex and holds the hosts' process lock on its registry for its lifetime, judged by pid and start time. A lock left by a crashed host is taken over; what that host left in flight is already marked unconfirmed and is never replayed. A second live host is refused. Preparation and optional DeepSeek compression happen outside the mutex. Promotion rechecks real native status, source revisions, task versions, input cursors and actual model/effort/Fast settings. Paused work handover is disabled by default.

`_kin/compact` runs only on an idle thread and always ends with a receipt (completed, failed, timeout or unknown) that `checkOnly` reads back. The host waits at most ten minutes for it. On timeout it leaves the dispatch mutex and records the operation as unconfirmed, with a failure receipt. An unconfirmed compaction is settled by evidence, never by a retry under its ID: the runtime's receipt for that ID, checked every five minutes; a completion in native history; or, after an hour with neither, the conclusion that it did not run. A reply that arrives after the host stopped waiting is kept as evidence and settles nothing by itself.

Automatic chat uses DeepSeek Flash / high. Substantive work and sustained creative production use GPT-6 Sol / medium with Fast requested as a service-tier preference; the actual response tier remains a separate runtime field and is not inferred from that preference. A low-stakes playful outcome such as finding or sharing a public meme or sticker remains eligible for chat: web, image, file or tool capability alone never escalates it. DeepSeek classifies the intended outcome and stakes.

Before automatic work starts, the router saves the complete verified profile it is leaving: provider identity and route kind, model, reasoning effort and service-tier preference. If any of those fields is unknown, the input is not submitted and is retried after 30 seconds, 2 minutes and 10 minutes; the previous profile is never guessed. The router restores that exact profile only after every open task, tool and required delivery has settled. One remaining task prevents an early restore. Automatic classification never overrides a manual profile. It stays until the owner selects another one or a work or auto control, or Kin requests work or plain automatic routing through `request_mobile_mode`. An explicit forced `auto` while work is open exits the manual pin immediately and selects the automatic work profile. The task and input version remain open, and the saved chat profile is restored only after full settlement.

Explicit natural-language manual, work or auto control from the real owner crosses a busy boundary immediately by default; it does not require an extra word such as “now”. DeepSeek sets `force=false` only when the owner expressly asks to wait for the current work or turn to finish. The host's `forceSwitch` callback must return `state: "interrupted"` or `state: "idle"` only after ACP cancellation (or an already-idle check) proves hot switching is safe. The router then advances its execution epoch, preserves task identity, input version and external-effect/send ledgers, and rejects late output from a canceled turn as authority for completion or sending. If the receipt is `interrupted`, a declaration Kin already made about the interrupted task (completed, partial, declined or deferred) stands; [mobile routing](mobile-routing.md) describes how tasks close. If the receipt is `idle`, a completion that was merely waiting for its original delivery receipt remains active and can settle without executing the work again. Already-sent platform messages remain delivery evidence. Unconfirmed cancellation or switching stays pending; a confirmed failure is reported as failure. Neither is phrased as success. System events, attachments and tool proposals cannot authorize force. After a confirmed force receipt, stale coordinator `processing` state from an old sender does not veto the switch, but native identity and `nativeStatus: "idle"` are still required.

After the first force boundary, prompt, tool and delivery observations must carry both `turnFence` and `inputVersion`. Reply manifests freeze that pair with the task binding before sending, pass it to every fragment and retain it on the bubble-level receipt; an existing manifest cannot be rebound to another execution. An unversioned, future-fence or mismatched observation is retained only as historical evidence. An explicit older-fence delivery keeps its actual message/outbox receipt under a fence-specific history key, so it can settle a completion intentionally preserved by an `idle` boundary without overwriting a current entry that reused the same ID.

The private host may recover a historical owner control that was accepted under the wrong semantic route through `reclassifyAcceptedControl`. It authenticates and reads the original source, runs the current DeepSeek classifier, then supplies the accepted input ID, its router semantic hash, a basis made of the configuration revision and the number of owner inputs since that one, the bounded control decision and this exact evidence summary: `{id, version, sourceSha256, acceptanceSha256, ownerBindingSha256, actualSessionId, conversationId, generation}`. The three digests are 64-character SHA-256 values; `sourceSha256` covers private source evidence and is intentionally distinct from the router semantic hash. The public receipt persists no owner identifier, text, attachment, path, URL or source bytes. It leaves the original `record.route` unchanged, appends one versioned reclassification receipt, supersedes older pending mode requests and applies a manual/auto/work request using that exact receipt as force authority. It never redispatches the old input or replays a tool, delivery or artifact. A byte-for-byte retry returns the existing receipt before the basis is checked; changed command IDs, non-owner or unaccepted sources, identity/hash mismatches, status/watch/non-control results, and evidence older than a later explicit owner control or reclassification are rejected.

After a host restart, the same coordinator restores the persisted full routing profile. Manual mode restores its chosen profile. Automatic work restores the saved pre-work profile only after all delivery obligations settle. Session-maintenance candidates freeze the router's verified provider identity and route kind, model, reasoning effort and service-tier preference at creation, reuse that profile for resume and verification, and compare it again before promotion. Every candidate `thread/start` and `thread/resume` receipt must independently confirm the configured model, isolated-process provider alias, reasoning effort and thread service-tier setting; request declarations are stored separately and never backfilled as response evidence. The returned service-tier field confirms thread configuration only, not the priority actually received by a particular inference. Missing provider facts wait instead of falling back from a model name; Sol Fast remains Fast only when the verified host profile says so. Pending native input or an unconfirmed modern transition blocks ordinary recovery. A transition that recorded model names but not its previous full profile is reconciled only when the live runtime already proves one of those endpoints; the host does not invent an effort or service tier. A pre-commit maintenance candidate without that profile evidence is retired and rebuilt from the current verified runtime once it is settled (created, injected, ready or waiting); an unconfirmed one, like an uncertain candidate whose binding was already committed, stays blocked for conservative reconciliation. No synthetic user message or new work task is created. Pressure measurement resumes from native history; a post-compaction context-size estimate is retained even when the native receipt has zero input/output counters.

Candidates use a separate read-only mobile app-server process with configured MCP servers disabled and no channel transport. The host injects public history with `thread/inject_items`, verifies its persisted marker, and runs a structured internal continuity check. This check is a host event, not a synthetic user message. Candidate-only execution restrictions are supplied by the process and verification turn rather than a permanent persona change. Promotion loads the new thread in the shared mobile ACP process and retires the old subscription.

DeepSeek's Responses API does not accept a named native `toolOutput` without a `call_id`. The gateway handles only the named continuity-check event: it supplies the public transcript as quoted historical data and the verification request as an internal event. This also avoids inventing reasoning state for imported assistant messages. Ordinary user/tool messages retain their existing roles; internal verification output never goes to channel transport. See the [App Server injection interface](https://learn.chatgpt.com/docs/app-server#inject-items-into-a-thread) and [DeepSeek Responses API](https://api-docs.deepseek.com/guides/responses_api/).

## Integration

The generic adapters are `session-manager.mjs`, `session-policy.mjs`, `native-window.mjs`, `native-candidate.mjs` and `mobile-session-host.mjs`. `codex-runtime-patch.mjs` holds the owned ACP's runtime, compaction, checkpoint injection, retirement, input-status and assessment extensions. It is applied once when an owned ACP entry is generated, and an anchor that does not match exactly once stops that generation; a new runtime reaches the phone only as a proved candidate ([mobile runtime](mobile-runtime.md)).

Host configuration supplies private paths and the existing model catalog. It does not modify desktop Codex settings. The durable registry is the authority for `conversationId`, `generation`, `threadId` and `nativeSessionId`; these are not inferred from each other. It is written and read like every other [durable adapter state file](mobile-recovery.md#durable-adapter-state), with one exception: when neither its current revision nor the kept previous one can be read, the manager refuses to open rather than starting fresh, because that binding is a fencing token and reopening at the first generation would let an older fence pass again. A fence is always checked against the current file, never against an older revision.

The registry is also the configuration of record. It changes only through a sourced `configure`; configured host values that differ from it are kept as `configDrift` for the operator. It is written only when its content changes, so a minute that changes nothing writes nothing. Settled review events leave after a week or beyond 64, finished compaction records beyond 50, retired candidates beyond 10, and settled owner requests after a week; nothing still open is dropped, and a floor keeps an older native compaction from being counted again.

| Host interface | Purpose |
| --- | --- |
| `read_mobile_runtime` | Current native model, generation, pressure, policy revision, advice and operation receipts |
| `request_session_rotation` | Register review/compact/rotate intent with a stable command ID; return without waiting for the current turn |
| `read_conversation_checkpoint` | Public checkpoint, sources, coverage and reading entry points |
| `configure_mobile_sessions` | Version-checked mobile policy changes with source and command receipts |
| `session-snapshot`, `session-checkpoint`, `session-validate` | Private host projections and dependency validation; the snapshot also carries the latest session judgment |
| `session-review` | Queue one maintenance appraisal for the observation the host wrote |

The router integration supplies a live non-secret model catalog and resolves a requested `{model, reasoningEffort, serviceTierPreference}` against it without nearest-value fallback. `switchModel(model, profile, {forceBoundary})` applies that resolved profile and returns the canonical runtime used for verification. `forceSwitch({sessionId, commandId, sourceInputId, reclassificationId, fromEpoch, toEpoch})` returns only `interrupted`, `idle`, `failed` or an explicitly unconfirmed state. `reclassificationId` is null for an ordinary owner control; when present, the private callback validates the exact stored receipt rather than treating the original misclassified route as force authority. Native observations and delivery receipts carry `turnFence` and `inputVersion`; receipts from an older fence remain evidence for their original external effect but cannot satisfy a later completion version. Successful switch notices name the verified reasoning effort. They may say that the Fast preference is configured, but never infer or claim an actual priority service tier from that preference.

`observe` and `compact` default to enabled; `prepare` and `rotate` default to disabled and change only through `configure`. The readiness switches never remove the completed-compaction and post-compaction-evidence requirements. `pausedTaskHandover` is disabled.

While dispatch is frozen — a release's freeze, a migration's or a hold, the same `router.frozen()` the mind's loop checks — the minute tick only reads, observes, records judgments and reconciles: native compactions, an unconfirmed compaction's receipt, an uncertain candidate's injection, and a promotion whose binding is already committed. It starts no checkpoint, compaction or rotation candidate. Each starts through the router's activity gate (`session-maintenance`), which refuses it under a freeze and otherwise counts it for the drain, never for the owner's dispatch, until it has ended: a compaction from its checkpoint on, a candidate from its creation to its promotion or abandonment. A freeze that arrives midway lets the running step finish and starts no further one: a candidate stops at the state it reached (created, injected or ready), and a compaction or a promotion is checked again under the coordinator, so neither starts and the binding a release or migration read stays. The judgment is kept, and the first tick after the thaw goes on from where it stopped (CL6-FLOW-02).

## Moving into Kin's Codex home

`commitMigration` is the registry's other way to a new generation. The private host's one-time migration into Kin's own Codex home (`migrate-kin-home`, run through `kin-deploy migrate`) freezes dispatch and waits for in-flight work, backs up the registry and routing state, builds a checkpoint at the fixed allowance, opens a thread on the new home, injects the checkpoint and verifies the thread's runtime, tool list and one read-only tool call. Only then does it stop the host and commit: the binding moves to generation g+1 on that thread in one write, made under the registry's lease, so a live holder is refused rather than waited out. The commit refuses a changed binding, a reused thread or an unsettled rotation, and it answers a repeated request with what it already did. Before the commit the old thread stays in use and a failure rolls back; after it the migration only goes forward and never binds the old thread again. The new segment records the home and its hash, and the checkpoint the thread was given is the one `read_conversation_checkpoint` serves.

## Validation and limits

Synthetic tests cover pressure calculation, compression before rotation, fifty prior compactions without automatic rotation, protected work, input races, candidate profile checks, stale sources, process leases, crash recovery, out-of-order compaction receipts, one review per cause and its backoff, compaction timeouts, fixed-allowance checkpoints, writes only on change, pruning, configuration drift and the migration commit. Python tests cover bounded checkpoints and maintenance-only appraisal commits. Each runtime candidate's native proof covers a maintenance candidate created in a separate app-server and loaded through the owned ACP, compaction followed by resume, and process restart ([mobile runtime](mobile-runtime.md)).

Keep private replay results, message bodies and native identifiers outside the public repository. A compatibility probe proves the tested path and version; it does not guarantee perfect conversational recall. Current-token measurements are distinct from cumulative usage, and a post-compaction input measurement may remain unknown until the next native turn. The system preserves uncertainty instead of treating a model's confidence as a successful operation or delivery receipt.


## Quiet assessment in the current session

With `main_session_review` enabled, action and emotion assessments and session reviews are answered by the current session's own model, in an ephemeral fork of the main thread made through `_kin/assess` (the default `fork` channel). The fork reads the thread up to its last completed turn and runs with the session's model, effort and provider, a read-only sandbox, no network and approval `never`. The memory tools run in their read-only mode and every other tool server is disabled. It answers under the assessment's output schema and is then dropped. The main thread never sees the assessment input; an assessment neither waits for the owner nor is preempted by her. A fork that fails, times out or is interrupted leaves the appraisal waiting with its usage recorded, and nothing falls back to the main session. The `legacy` channel instead runs a quiet turn in the idle main session, which owner input cancels. The host records every completed assessment turn with its fork. No model switch or phone delivery is implied by an assessment.

The local minute timer only checks state. The session decides its next review, from ten minutes to a day ahead, and may recall, write a sourced personal reflection, plan an authorized activity or leave these fields empty. Exploration remains an independent executor; its final observations and open questions feed the same main-session appraisal. Persona defaults, inferred traits, public experiences and private reflections retain their different evidence classes.

With `native_window_context`, no 12,000-token ledger caps automatic background. Each automatic injection stays within the fixed 8,000-token ceiling and the room the native window reports, and relevance selects what fits; output/tool reserves, native compaction and explicit recall take care of the rest. Delivery identity, source revisions, epoch and accepted native receipts remain authoritative; the absence of a quota does not mark prepared context as read. A checkpoint has the same fixed ceiling and stays incomplete when required facts cannot fit.

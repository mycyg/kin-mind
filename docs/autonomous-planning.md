# Memory-backed autonomous planning

Kin forms goals and reviews actions with DeepSeek Flash / high. Memories, four recent timestamped public turns, unresolved matters, artifacts, exploration outcomes, sharing receipts, plans and available capabilities enter the existing appraisal. A score is context, never an execution threshold. A missing or stale decision waits for review.

Affect scores and short-term motivation targets continue to rise or fall with sourced conversation, memory and outcomes, and evolve over time using their configured half-lives. DS may update `action_decisions.strength` (0–100) even when waiting or abandoning. Existing wish strength is retained if omitted; a new wish uses its current motivation instead of a fixed default. Neither a high nor a low score grants or revokes execution by itself.

## Decisions, plans and execution

The `semantic_actions` flag replaces the legacy 75-point contact/exploration gates at candidate selection, claim and pre-send validation. Quiet hours, current contact preferences, user work priority, channel permissions and source/version validation remain authoritative. Normal chat reuses the existing input classifier's `recall` decision; it does not add a fixed model call. Optional memory expansion is capped at three rounds and 150 seconds, with each reranker capped at 30 seconds. Optional failures return verified local evidence and explicit gaps.

Plans have stable IDs, revisions, goal, motivation, source references, next review time and a dependency graph of steps. Actors are `explore`, `create`, `contact` and `owner`. Each step records its goal, completion criterion, Singapore time window, prerequisites, inputs and optional `owner_request_id`. Long-term plans have no seven-day expiration. A time window opening or being missed triggers another review. Restart never authorizes accumulated catch-up messages.

Reviews are edge-triggered. Each distinct reason — a due review time, a changed or superseded plan source, a new owner message, a new agent version, or a ready step that can no longer run as decided — wakes one review and is then recorded as answered in `mind_plan_wakeups`. A condition that merely stays true wakes nothing more, and separate reasons that happen to coincide still cost one review. A review set aside before it read the plan reopens the reasons it had taken; one that already read the plan keeps them answered. `decide` stamps the current agent version, so a configuration upgrade is reviewed once instead of on every host minute.

DS proposes plan changes and `execute`, `wait`, `abandon`, `owner_accepted`, `owner_completed` or `owner_declined`. The host checks the supplied source manifest and expected revision in the appraisal transaction. Owner participation requires an actual owner source. A proposal, delivered invitation, acceptance and completion remain distinct. A model cannot settle Kin execution or manufacture a channel receipt.

The host also records the plan view an evaluation was actually shown, and applies each decision only while the target step's revision, state and decision ID still match it, and while the basis that decision rested on is unchanged: the step definition, the revision, state and receipts of every step it depends on, the plan's goal, motivation and evidence revisions, and the owner epoch. A decision that lost that fence is held, never raised — `plan-inactive`, `view-missing`, `step-touched` or `basis-changed` is recorded with the committed result, the rest of the evaluation still commits, and one coalesced review asks again. So a stale `wait` cannot overwrite a newer `execute`. A stale expected revision is rebased only when the step and its basis are provably unchanged, and a rebased decision cannot postpone a review that the revision it never saw had asked for. Without a recorded view an exact revision remains the only proof, as before.

A `wait` that repeats the stored decision unchanged — same action, strength, selected delivery artifacts, procedures and accounted preconditions — is written to `mind_plan_reviews` and advances only the next review time. No plan revision is spent, so no other evaluation's expected revision is invalidated and the stored decision stays current; any changed business field such as strength takes the normal path and bumps the revision as before. A completed review registers the agent version for every plan it was shown, including plans whose decisions were held; a plan it could not show registers nothing and keeps its wake-up reasons open. A review time that is not in the future is treated as omitted: a decision falls back to twenty minutes ahead and a plan change asks for a review at once, while the model's own value stays in the audit row.

Kimi receives a question plus actual memory excerpts, known findings, gaps and recent dialogue. The creator uses the configured work model in an isolated Codex CLI workspace, with a separate native execution receipt. It does not resume the phone session, load its MCP tools, send messages or write shared state. One creator and one explorer may run initially; owner work preempts them and preserves checkpoints. The host verifies artifact containment, size, hashes, inspectable content and a separate DS completion review. Delivery requires a subsequent DS decision selecting verified artifact hashes, followed by the existing durable channel outbox. An uncertain send is reconciled with the same ID.

## Storage, APIs and feature flags

Additive SQLite tables store plans/history, fenced runs, the shared model-lease ledger, procedural memory/history/trials, effective-use events and independent strength observations. `mind_plan_reviews` keeps reviews that are not revisions — a repeated unchanged wait, and the agent version a completed review registered — with the reason, decision and provider receipt of each; `mind_plan_wakeups` keeps one row per answered wake-up reason. Both are created on demand and read by nobody else, so an older host ignores them and a rollback leaves them in place. Model calls run outside write transactions; source, revision and lease checks fence late results. Existing desires migrate by stable identity without granting execution.

| Interface | Contract |
| --- | --- |
| `read_autonomous_plans` / `GET /v1/autonomy/plans` | Scope, optional ID/status, pagination and history; returns revisions and waiting reasons. |
| `manage_autonomous_plan` / `POST /v1/autonomy/plans` | Idempotent `command_id`; create/update/pause/resume/reschedule/cancel. Changes require expected revision and sourced reason. |
| `read_procedure_memory` / `GET /v1/autonomy/procedures` | Sourced method candidates, validity and dependency review state. DS judges applicability. |
| Private `plan-claim/renew/result/interrupt/recover` | Host executor receipts; unavailable as model completion tools. Recovery requires stopped workers. |

Independent flags: `semantic_actions`, `autonomous_plans`, `creative_execution`, `usage_reinforcement`, `procedure_learning`, `reinforcement_ranking`. They default off. Existing lifecycle and temperature flags retain their meanings. Turn off the affected path to roll back; retain new chats, plan history, source records, files and delivery receipts.

`plan_review_record_only` is a separate optimization switch in the memory configuration and defaults on; only an explicit `false`, set through `configure-memory`, restores the previous behaviour, where a repeated unchanged wait spends a plan revision. Edge-triggered wake-ups, the recorded plan view and held decisions are not covered by it and stay in force either way.

## Effective use and learned methods

Effective use is counted for explicit queries, actual reply references and verified task results. Deduplication spans channels and origins by authenticated input ID; all steps of a plan share one use key. Candidate hits, automatic background injection, maintenance, summaries and planning do not heat memory. Decayed frequency has a 30-day half-life and `log1p` strength. It does not alter confidence or revive corrected facts.

Frequency collection and ranking are separate. The new weight version starts its own seven-day observation. Ranking cannot be enabled using an older temperature trial: seven consecutive actual observation days, seven full elapsed days, version-matched replay evidence and an owner decision are required. Shadow metrics record proposed ranking differences while production order remains unchanged.

A procedure preserves applicability, steps, tool/environment versions, success criteria, counterexamples and actual outcome sources. It remains a candidate until two distinct recorded cases pass isolated replay. External effects use existing genuine receipts; tests never resend phone content. Source changes, counterexamples, agent configuration changes or unavailable environment versions prevent current execution. Methods cannot edit persona or permissions.

## Concurrency, accounting and validation

Keyword, vector and graph candidates are read concurrently. Different event digests can run in parallel, with one valid generation per event. One shared database ledger admits every model call on the lane its caller declares, with background concurrency a configurable 1–8; the lanes and their waits are below. User work prevents claiming new low-priority jobs. A structured decision is cached under the digest of the fully rendered request together with the judgment it answers, becomes servable only once the caller reports that it validated the result, lives at most five minutes, and is dropped as soon as a source, record or graph object it rested on changes. A cache hit is recorded as a reused call and claims no token consumption. Timed-out requests retain unknown usage; late usage receipts remain separate from effective results.

Run `pytest -q` and `node --test adapters/*.test.mjs`. Synthetic planning cases cover long horizons, time windows, dependency cycles, owner participation, changes, restart, concurrency, partial delivery and unavailable models. Private release validation uses a frozen 48-case history set and a separate real-model planning replay. Required history gates remain 21/21 critical cases and at least 44/48 top-eight hits. Measure warm local candidate P95 separately from network/model latency and total token cost. Keep private chats, replay inputs, credentials and plans outside Git.

The engineering references inform design, not a claim of measured Kin savings: [CoALA](https://arxiv.org/abs/2309.02427), [Mem0](https://arxiv.org/abs/2504.19413), and [Snowflake's agent context layer](https://www.snowflake.com/en/blog/agent-context-layer-trustworthy-data-agents/). Original evidence, versioned views and reversible state remain the system's authority.

## Reply review, admission waits and step verification

The private `share-preflight-group` operation reviews a whole reply once with its authenticated input, public dialogue, registered sources and delivery history. DS returns allow/revise/hold with every original bubble ID. Holds remain pending. Only an actual `choose_reply` receipt may resolve an input as silent or merged. Reviewed bodies freeze before transport; restarts reconcile original IDs and validate evidence without rewriting a partial reply. Input-specific health does not count a model-switch notice or an old reply as completion.

A reply too long for one call is reviewed in chunks instead of being refused. A chunk holds at most 48 bubbles or 120,000 characters and never divides a bubble, so a single oversize bubble stands alone as its own chunk. Every chunk carries the whole reply's ordered outline, the decisions the earlier chunks reached and the union of the findings the group cites, and must return exactly its own bubbles in order: a chunk that omits or reorders them is refused and never stored. Each chunk is written to `mind_reply_review_chunks` the moment it is judged, so a crash, a refusal or the host's own timeout never buys the same chunk twice. Two bounds surface as ordinary pending reasons rather than as failures: a reply needing more than sixteen chunks reports `reply-exceeds-review-capacity`, which the host may answer by retiring the group, and a review that runs past its 150-second wall clock stops on a chunk boundary and reports how many chunks of how many it finished, so the next resume pays only for the rest. The merged receipt keeps every chunk's own accounting; a chunk that reported no usage is recorded as unknown, never as zero.

When an earlier reply was interrupted, its unsent items travel with the next reply's review as `remainder`. The review reports in `covers_remainder` which of them this reply already says, naming the item and the bubble that carries it; whatever it does not mention is returned as `remainder_owed` and keeps waiting. A covered item hands its content reservation to the bubble that covers it, and an item nobody covered keeps holding the content it still owes. A group that was already partly sent is never rewritten: its sent bubbles travel as context that is never changed and never sent again, only its unsent remainder is judged, and a remainder that cannot go out as written is held so the host retires it and starts a new group. The switch is `chunked_reply_review`; with it off the single-call limits return and a group past them is refused outright.

`configure-model-capacity` sets one database-wide background limit; the host's `background_model_limit` is written to the same place at start-up, and a missing limit is reported (`model_capacity_unconfigured`, `source: "default-unconfigured"`) rather than silently assumed. Admission has three lanes chosen from the caller's declared purpose: background, a reserved user-work slot that does not yield to foreground sessions, and foreground, which is always admitted and only recorded; see [model lanes](kin-mind.md#model-lanes-and-the-lease-interface). Pre-request capacity and foreground waits have separate counters/backoff and do not consume error attempts. An entire appraisal reuses an admitted lease. Actual failures, partial work and uncertain usage remain recorded. Sourced, bounded admission-only recovery preserves job IDs/history and never reuses an old proposal as a new decision.

Completion review separates `step_remaining`, `downstream` and `advisory`. Legacy `remaining` remains a current-step gap; executor notes are evidence for DS classification. Produced artifacts retain `phase=needs_verification`, `verification_gaps`, a checkpoint and resume action when checks are missing. Artifact hashes and current evidence are checked again after DS returns. Later delivery and owner responses are separate steps.

The optional `CreationVerifier` uses a host-configured Playwright module and browser in a bounded child process. Static HTML is rendered at 390 and 1024 pixels with page scripts, external resources, network, downloads and service workers disabled. Source/image hashes and PNG dimensions are verified again by the result host. Rendering is evidence of output and layout, not an independent aesthetic review. No screenshot or failed rendering can be converted into a successful check. `wholeReplyReview` and the optional verifier can be disabled independently; keep journals, sources and receipts.
